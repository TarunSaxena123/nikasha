Nikasha: how it was designed and built

An educational backtester for Nifty 50 options, built spec-first with Claude in three days (14–16 October 2026). This page explains the architecture, the decisions and their trade-offs, the problems met along the way, how it was tested, and the questions an interviewer is likely to ask.

The problem and the product

Retail options traders often risk money on strategies they have never tested, and the strategies usually exist as notes with vague rules.

Untestable rules

"Exit if it closes decisively below", "reduce size significantly". A computer can't test that as written.

Results without reasons

A profit number alone doesn't say when a strategy works, or whether the result is luck fitted to the past.

No safe start

Beginners don't know the terms and have no safe way to learn why most strategies fail.

What Nikasha does

  1. Describe: upload or paste a strategy document, build it step by step, or start from a template.
  2. Clarify: it never guesses. It asks only for missing mandatory inputs and vague rules, then shows the rules in plain English.
  3. Evaluate: the strategy is replayed minute by minute on the historical data, with option premiums modelled from the index and India VIX.
  4. Understand: a report that puts risk before profit: plain-English summary, breakdowns by year, volatility and market regime, an overfitting check, a volatility sensitivity check and "what-if" ideas. PDF and CSV are made in the browser.

Nikasha is educational, not advisory. It gives no signals or recommendations; ideas are worded as "this change would have…" on past simulated results. A full disclaimer (not SEBI-registered, modelled prices, unofficial data source) must be accepted before any strategy screen.

The spec-driven process

No application code was written until every spec was approved. After that, every change in behaviour went through the spec first.

  1. Brief (claude.ai): idea, scope, name, data, disclaimer and spec structure agreed in a planning chat, handed over as NIKASHA_BRIEF.md.
  2. Clarify: Claude Code asked 22 grouped questions (fill timing, strike rounding, costs, overfitting threshold…) before writing anything.
  3. Project-level specs: constitution.md (11 non-negotiable principles) and product.md (complete requirements), then architecture.md, frontend.md, backend.md and the contracts.
  4. Contracts: an OpenAPI 3.1 file and JSON Schemas for the strategy and instrument formats, plus strategy-rules.md for rules a schema can't express (SEM-01…25) and shared fixtures both sides must agree on.
  5. Feature specs: seven folders, each with requirements.md in EARS form ("WHEN … THE SYSTEM SHALL …") with acceptance criteria, design.md with fixed Frontend / Backend / Contract sections, and tasks.md tagged [FE], [BE] or [CONTRACT]. Two quality gates ran before tasks were approved: clarify, and a consistency check.
  6. Traceability: traceability.md maps each requirement to its design section, task and test, with status.
  7. Build, then change process: features built and tested in order. Every later change was classified (behaviour change, bug fix or refactor); behaviour changes were proposed, approved and logged in CHANGELOG.md before code.

Key decisions and trade-offs

Each decision, why it was made, and what it costs.

1. Model option premiums instead of using real option prices

Only Nifty spot and India VIX minute data were available. Premiums are priced with Black-Scholes using VIX as volatility.

Trade-off: VIX is a 30-day, near-the-money measure, so skew and expiry-day behaviour aren't captured. Mitigation: a "modelled, not actual" badge on every report and the VIX ±2 sensitivity rerun. A PricingProvider interface leaves room for real data later.

2. Use the AI model only to read documents, never to produce results

The model turns free text into candidate rules. Every number and every summary sentence in a report comes from the engine with fixed sentence patterns.

Trade-off: summaries are less fluent than generated prose, but they are deterministic, testable and can't invent figures. Tests replay recorded model responses, so CI never calls a paid service.

3. Never guess; no hidden defaults

Thirteen mandatory inputs; anything missing or vague is asked. Advanced options are off unless set. The only pre-filled values (lots, lot size, costs, period) must be confirmed before evaluation.

Trade-off: more questions for the user, but every result reflects rules the user actually stated, and the report lists every setting used.

4. Zero data storage

No database, accounts or files. Uploads are read in memory; logs carry no user content; reports live in the browser tab; PDF and CSV are generated client-side.

Trade-off: no saved strategies and no "come back later". A privacy marker test proves a unique string from a test upload never reaches the logs.

5. Browser calls Lambda Function URLs directly

No API Gateway and no Vercel functions in the path.

Trade-off: CORS and the browser's content security policy must name the exact URLs, and cold starts are visible to the user. In return: free tier only, and Vercel never sees user content.

6. Data baked into the engine image, loaded on first request

Eleven years of minute data ship as Parquet inside the container; no S3.

Trade-off: a data update means a new image; the first request after idle pays about 8 seconds of cold start.

7. Guard against overfitting

Weekly-expiry strategies are tuned on 2019–2023 and checked on 2024 to May 2026. A strategy is flagged "possibly overfit" when unseen-period expectancy falls below half of the tuning period's (or changes sign), with at least 30 trades in each part.

Trade-off: fewer years for the main result, but suggestions can't simply chase the past.

8. Fixed rules wherever the market is ambiguous

Signals fire on candle close and fill at the next minute's open; if stop and target are hit in the same minute, the stop counts (conservative). Expiry dates are derived from the rules (Thursday weekly expiry until August 2025, Tuesday from 1 September 2025) and the trading days actually in the data. Missing minutes are never filled.

Trade-off: results can differ from a broker's fills, but every rule is written down, tested and disclosed.

Known limitations and what's next

Limitations

  • Premiums are modelled, not real; expiry-day results are the least reliable.
  • The data is an unofficial Kaggle dataset used for education only.
  • Today's lot size and costs are applied to the whole history.
  • Nothing is saved; closing the tab loses the report unless downloaded.
  • About 8 seconds of cold start after the engine has been idle.

Next steps

  • Bank Nifty and Sensex, then MCX crude through new instrument profiles (Black-76 pricing for options on futures).
  • Real option-premium data behind the same pricing interface.
  • A long-term host before the AWS Free plan ends; the engine container is portable.
  • Legal review of the disclaimer before any public launch.

About the design and process

What is spec-driven development, and how did you apply it here?

The specification is the source of truth and code follows it. I wrote a constitution, a complete product spec, architecture, frontend and backend specs, contracts, and seven feature specs with EARS requirements and acceptance criteria, all approved before any code. Every one of the 230 requirements is traced to a design section, a task and a test. After that, every behaviour change went through a proposal, approval and a changelog entry before code changed.

Why EARS for requirements?

"WHEN … THE SYSTEM SHALL …" forces a trigger and a single observable outcome, so each requirement is unambiguous and turns directly into a test. Given/When/Then acceptance criteria then give the concrete examples.

How did you keep the frontend and backend from disagreeing?

They are built only against shared contracts: OpenAPI 3.1 plus JSON Schemas. Types are generated for both Python and TypeScript, CI fails if generated code drifts, and shared fixtures must validate the same way on both sides. Rules a schema can't express are numbered in strategy-rules.md and tested on both sides.

You have no option price data. How can the backtest be trusted?

It's an educational tool and says so. Premiums come from Black-Scholes with India VIX; every report carries a "modelled, not actual" badge and reruns with VIX ±2 points so you can see how much results depend on that assumption. The pricing sits behind an interface, so real option data can replace it without touching the backtest.

Where is the AI used, and why only there?

Only to read an uploaded or pasted strategy into candidate rules. Results, numbers and summary text are all computed by deterministic code, because an AI shouldn't be able to invent a win rate. The AI output is a flat structured schema converted by tested code, vague items always become questions, and CI replays recorded responses so no test spends money.

How do you handle missing or vague inputs?

There are 13 mandatory inputs, and one completeness check in the browser is shared by the builder, the upload flow and the review screen. Missing inputs and vague words ("decisively", ranges like "30–35", "Thursday" for expiry) are asked one at a time; the Evaluate button stays disabled until everything is answered. Text that isn't a trading rule is ignored.

How did you guard against overfitting?

The data is split: 2019–2023 for tuning and 2024 onward as unseen data. The report flags "possibly overfit" when unseen-period expectancy drops below half, or changes sign, with at least 30 trades in each part, and says "too few trades to judge" otherwise. Suggestions are checked against the unseen period instead of being ranked as "best".

Walk me through the architecture.

Vercel serves a static Next.js app. The browser calls two AWS Lambda functions directly through Function URLs: the engine (a Python container with the market data inside) and the extraction function (the only holder of the Anthropic key). There's no database, queue or object store. CORS and the content security policy allow only the production domain and the two exact URLs.

How did you achieve zero data storage, and how do you prove it?

Uploads are read in memory and discarded, logs record only technical errors through a shared logging helper, the report lives in the tab, and PDF and CSV are generated in the browser. The only thing kept is the disclaimer acceptance flag in the user's own browser. A privacy marker test puts a unique string in a test upload and strategy and checks it never appears in either function's logs. The disclaimer also discloses that strategy text goes to the AI provider.

What was the hardest problem?

Two stand out. Getting time right: the weekly expiry moved from Thursday to Tuesday in September 2025, so the expiry calendar is derived from dated rules and the data's real trading days. And deployment: the AWS Free plan only allowed one region, and loading the data at import time exceeded Lambda's 10-second init limit (17.6 s cold start), fixed by loading on first request (about 8 s).

How did you handle a change request after the specs were approved?

The owner uploaded an opening-range + CPR strategy that Nikasha couldn't test. I classified it as a behaviour change, proposed new requirements and semantics with acceptance criteria, got approval, logged it in the changelog, updated contracts and traceability, wrote tests, then the code. During that work a new question came up ("profit booking at R1" when the index is already past R1); it was recorded as a pending decision, the owner chose the rule, and it went into the spec before the code.

How is it tested, and what runs in CI?

About 370 automated tests: engine (211, hand-calculated cases and golden reports), extraction (39, recorded responses), web unit (60) and Playwright end-to-end (59, on desktop and phone sizes, with accessibility scans). CI also runs lint and types, contract checks, generated-code drift, a hashed product-name scan, the README disclaimer sync and SAM template rules.

What would you change with more time or a budget?

Real option-premium data, more instruments through profiles, keeping the engine warm to remove cold starts, saved strategies with explicit consent, and a legal review before any public launch.

How did you work with Claude, and how did you keep control?

Planning happened on claude.ai and produced the brief; Claude Code then wrote the specs and the code. I approved each spec step, answered clarifying questions, and decided open points (a pending-review list of 27 readings). A CLAUDE.md file made the rules permanent: spec first, never guess, no product names, no paid calls in tests. The full session transcript is published alongside the app.

About the functionality

What can a user put into a strategy?

Mandatory inputs (13): instrument, buy or sell, Call / Put / both (Call on the bullish signal, Put on the bearish one), ATM / ITM / OTM with the distance in points (a multiple of 50), expiry (current weekly, next weekly or monthly), candle timeframe (1, 3, 5, 15, 30 or 60 minutes, or 4 hours), intraday or positional, number of lots, lot size, an entry trigger, a stop-loss and an exit rule.

Entry conditions: EMA, SMA, RSI, ADX, MACD, Bollinger Bands, Supertrend, opening range, daily pivots / CPR, candle range and body, price and VIX, compared with "above / below", "crosses", "turns up / down" or "rising / falling over N candles", grouped with AND / OR. The Put side can be mirrored from the Call side in one click. A fixed entry time works too.

15 advanced options, all off unless set: SL cap, trigger-candle stop-loss, risk-reward target, trail stop to cost, exit after N candles, exit conditions, index-level target, partial exit, VIX sizing, entry and no-entry windows, expiry-day cutoff, daily limits, multiple legs, and strike by delta or premium.

Walk me through the upload flow with an example.

Paste "Buy ATM Nifty call when RSI 14 crosses above 60 on 5-minute chart, stop-loss 30%." The extraction function reads it and returns what it found (buy, Call, ATM, 5-minute, RSI condition, 30% stop). The browser's completeness check then asks only what is missing, one question at a time: the exit rule, intraday or positional, expiry, and confirming lots and lot size. Nothing about advanced options is asked. The user lands on the review screen with the rules in plain English and clicks Evaluate Strategy.

For a long document, vague wording ("closes decisively above", "SL 30–35") becomes a question, rules Nikasha can't test are listed as left out and must be acknowledged, and unrelated text is ignored.

Which exits are supported, and which one wins?

Stop-loss (% of premium, points, or the trigger candle's low/high, optionally capped), target (% of premium, points, risk-reward or an index level such as R2), trail stop to cost, exit after N candles, exit conditions (filled at the next minute's open), partial exits (book part of the position, then keep the stop, move it to cost or trail it), a time exit, and the 15:15 intraday square-off.

Every open trade is checked on each 1-minute bar. If the stop and the target are both hit in the same minute, the stop counts, the conservative reading. An index level is used only if it lies on the trade's profitable side at entry.

How do intraday and positional trades differ?

Intraday positions are always closed at 15:15. For a positional strategy with no target or time exit, Nikasha asks what to do (hold until expiry, exit at a set time on expiry day, set a target, or exit after N candles) rather than choosing for the user. A position still open on its expiry day is settled at intrinsic value, because Nifty options are cash-settled. Entries whose expiry falls after the last day of data are skipped and counted.

How is the strike chosen and the premium calculated?

The signal fires on a candle's close and the trade fills at the next minute's open. ATM is the spot rounded to the nearest 50 (a half rounds up); ITM and OTM move from there by the chosen distance. The premium is priced with Black-Scholes from that minute's spot, the strike, India VIX as volatility, the minutes left to expiry and a 6.5% risk-free rate. If that minute can't be priced (for example, VIX is missing), the entry is skipped rather than filled with a guessed price.

What does the report show?

Risk first: maximum drawdown and the worst losing streak, then net P&L after costs, win rate, average win and loss, and expectancy. It includes an equity curve and drawdown chart; breakdowns by year, month, VIX band, market regime (trending / mixed / sideways by daily ADX), weekday and Calls vs Puts; in-sample vs unseen-period results with the overfitting status; and the VIX ±2 sensitivity. It ends with a plain-English summary, the settings used and the advanced options that were off, skipped signals and data gaps, and the trade list. Everything is calculated on the selected period only, and the report downloads as PDF, with trades as CSV.

How are transaction costs handled?

Pre-filled and editable: ₹20 brokerage per order, the current statutory charges (STT, exchange, SEBI, stamp duty and GST) and slippage of 0.5 premium points per side. The user must confirm them before evaluating. Today's rates are applied to the whole history, the same way the lot size is, and each order is charged for its own quantity, so a partial exit pays its own charges.

What do "ideas" and the what-if sliders do?

What-if: sliders for the stop-loss and target. When a slider settles, a copy of the strategy with only that value changed is re-evaluated on the same period, and the report says, for example, "With a stop-loss of 25% instead of 30%…".

Ideas: on "Show ideas", Nikasha runs variants on the same period (stop-loss and target sweeps, a VIX-band filter, Calls-only or Puts-only, and one template alternative), four at a time. Each shows a reason and its result on the whole period and on the unseen period. They are never ranked as "best" and are worded as "this change would have…", because Nikasha doesn't give advice.

What does a beginner get?

An intro page explaining what Nikasha is and isn't, a "Choose a path" page, and three templates: Simple Trend Follower (9/21 EMA crossover), Higher-Timeframe Trend (1-hour) and a short straddle that shows how option selling behaves. "Use this template" goes straight to the review screen, so one click on Evaluate runs it. Every field has a tooltip, there is a glossary and six Learn articles, and the progress screen offers reading while the evaluation runs.

What happens with data gaps or conflicting signals?

Missing minutes are never filled. A minute with Nifty but no VIX can't be priced, so no entry or exit happens there; 2019-07-02, which has no VIX at all, is skipped. If the Call and Put conditions are both true on the same candle, neither trade is taken. Every skip is counted in the report with its reason, and the date range shown everywhere is read from the data itself.

About the name

Why the name Nikasha?

It's Sanskrit for touchstone, the stone used to test whether gold is genuine. Nikasha tests whether a trading strategy's edge is real.
